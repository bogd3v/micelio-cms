# Fediverse cut-over: from the local plugin to `@micelio/strapi-plugin-fediverse`

**Kind:** explanation, with the plan of one piece of work. What of the fediverse work of milestone "Micelio · Fediverso usable desde el admin" (epic #295) moves to `@micelio/strapi-plugin-core`, what moves to the published plugin as it is, and what is dropped at release line `0.7` (ADR-0017, sections 1, 5 and 6, in `bogd3v/micelio`). It changes no code. How federation works today is in [FEDIVERSE.md](../FEDIVERSE.md).

Checked on 2026-10-28 against `micelio-cms` `main` at `1d8f43c` (`@micelio/strapi-plugin-core` `0.2.0`) and `micelio-plugin-core` `main` at `87b47d4` (`0.3.0`): `docs/plugins/extension-points.md`, `docs/hooks.md`, `docs/api.md` and `docs/export-format.md`. The extension points are those of bogd3v/micelio-plugin-core#41 (merged in its PR #67). The spike is bogd3v/micelio-cms#316 and its amendments to ADR-0017.

## What the core offers

The package is the core's `strapi-server` export; everything below is reached through `strapi.plugin('micelio')`. Strapi does not order plugins by dependency, so a sibling plugin uses `service('extensions')` and `service('hooks')` from its `register`, which exist from the start.

The code and the behaviour travel to the package unchanged; the only change is that each row and each key names its site (ADR-0017, section 4). The content type UIDs stay `plugin::fediverse.*`, because the plugin's name does not change, so roles, tokens and layouts keep pointing at them.

## 3. Dropped at the cut-over

A `0.7` breaking change (ADR-0017, section 6; before 1.0.0 it needs the `!`, a `BREAKING CHANGE:` paragraph and the upgrade notes, standard section 7). The package never carries these.

| Dropped                                                                                                                                | Replaced by                                                                                                           |
| -------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `FEDIVERSE_ACTOR_USERNAME`, `_NAME`, `_SUMMARY`, `_SOURCE_URL` and their fallbacks and boot warnings (`utils/deprecated-variables.ts`) | The fields of the site's `fediverse` profile (Content Manager → Site → Fediverse). Already tracked as #307, see below |
| `global.fediverseHeader` as the header fallback                                                                                        | The `header` of the same profile (#307 copies it)                                                                     |
| `FEDIVERSE_HANDLE_HOST`                                                                                                                | The first host of the site                                                                                            |
| The attribution list (`utils/attribution-domains.ts`: host of `FRONTEND_URL` plus `FEDIVERSE_HANDLE_HOST`)                             | The site's hosts                                                                                                      |

**#307 already is the in-tree removal of the four `FEDIVERSE_ACTOR_*` variables and the `global` header.** It must merge before the plugin is moved, or the package inherits what it must not carry. This plan adds what #307 does not: the handle host and the attribution list, which need the site's hosts to exist.

**Variables that are not dropped** (the issue's list is exact, and a drop is a breaking change): `FEDIVERSE_ENABLED`, `FEDIVERSE_ACTOR_IDENTIFIER` (the actor id; it is the default site's actor path, other sites are an open decision below), `URL`, `FRONTEND_URL` (the distribution uses it for CORS and for the admin's `frame-src`, D4 of #360, and the boot seeds the default site's `url` from it, #372), `FRONTEND_ARTICLE_PATH`. `FRONTEND_DEFAULT_LOCALE` becomes redundant with `site.defaultLocale`: the package reads the site first and the variable only when the site has none, and logs a deprecation warning. Dropping it is a later `0.y`; the upgrade notes below say so.

### Upgrade notes draft for 0.7

> **Fediverse: settings move into the site.** `@micelio/strapi-plugin-fediverse` replaces the plugin inside `micelio-cms`. Federation is still off unless `FEDIVERSE_ENABLED=true`. Your followers, their blocks, the delivery queue and the actor key are kept; the actor id and the handle do not change. Take a backup first.
>
> What stops working, and what to set instead. Move the four `FEDIVERSE_ACTOR_*` values **before** you upgrade, in the 0.6 admin: a 0.7 boot with one of them set stops with a message that names it (#307). The first 0.7 boot pins your current handle host (`FEDIVERSE_HANDLE_HOST`, or the host of `URL` when it is unset) as the first of the site's hosts and records that it did; later boots ignore the variable with a warning that names it. Remove it afterwards.

Upgrade the CMS first, then the frontend of the previous MINOR keeps working.

## Gaps the plan found

The issue assumed these; the core and the code say otherwise. Each has a recommendation; the maintainer decides what is not marked as settled.

1. **`afterPublish` does not fire for articles yet.** The hooks run from the `transitions` service, which publishes only types made with `withEditorial`. `api::article.article` is not one, and putting the editorial workflow on host types is out of #360 (its decision D7, with the builder's review flow, bogd3v/micelio-plugin-core#57). Until then the only observable publish is `entry.publish` on `strapi.eventHub` (`CLAUDE.md`, pitfalls). _Recommendation:_ the package subscribes to **both**: the hooks for a type that has the `editorial` component, `eventHub` for one that has not, so an article is federated by exactly one of them (and `federateArticle` stays idempotent per `documentId` and `locale`, as the hooks reference asks, because a type that gains `withEditorial` later emits both for a while). The cut-over then does not wait for D7, and the "Triggered by `afterPublish`" row of section 1 becomes true when articles join the workflow.
2. **No admin renders a site section's `panel`.** `registerSiteSection` keeps the `panel` name and answers it; the core's reference says the Sites view that renders it "is a separate piece of the admin", and the core has no Sites page yet. With the profile in the core's own `site.fediverse` (Content Manager), the panel is no longer needed for the cut-over: the profile edits as the core's component, and only `identifier` and the explanation of the username lock would use it. _Recommendation:_ keep issue 1 as an improvement that nothing waits for; neither issue 4 nor issue 7 depends on it. The same Content Manager rule applies to both: any role with read or update on `Site` sees and edits the profile (decision D9 of #360 gives Editor and Author read on it), and the core does not narrow it. Accept it, because the profile is public in the actor document; if a role must not edit it, issue 7 restricts the `fields` of that role and tests it.
3. **The username lock is the package's, not the core's.** Section 1 says so; it is a Document Service middleware on `site.fediverse.username` plus a message, tested with a follower row.
4. **The admin bundle follows `enabled`.** #299 found that a plugin's admin code is bundled only if the plugin is enabled while the admin is built, and the image is built with `FEDIVERSE_ENABLED` unset, which is why the panel is registered from the root admin app today. A package has the same rule. _Recommendation:_ the distribution enables the plugin always and the plugin reads `FEDIVERSE_ENABLED` itself (no routes, content types or hooks when off). Side effect to verify, not assume: with the plugin always enabled its permission actions are always registered, which also ends "granted roles are lost when federation is turned off" (#300). This is a change of the operator interface, so it is tested in issue 7.
5. **One actor per site needs an actor path per site.** `FEDIVERSE_ACTOR_IDENTIFIER` names one, and `micelio-site.fediverse` has no such field. _Recommendation:_ the package's site section `fediverse-actor` holds an `identifier` (no default, so "unset" is detectable), immutable once set; the boot fills the default site's from the variable, and a new site defaults to its `slug`. The alternative is a core issue that adds `identifier` to `micelio-site.fediverse` (a MINOR of the core); it costs a release of the core and is not needed. The variable stays the default site's source until a later `0.y` removes it.
6. **Keys in the archive.** The private key is encrypted with this instance's `ENCRYPTION_KEY`, so an archive that carries it is useless on an instance with another key and dangerous on one with the same. _Recommendation:_ the section exports followers and blocks only; a restored site gets a new key pair, and remote servers refresh the actor. A `security` review decides before issue 6 ships ([data.md](../security/data.md) classes the key as Restricted).
7. **The handle host and `hosts`.** On 0.6 the handle host is `FEDIVERSE_HANDLE_HOST` when set and the host of `URL` (the CMS) when not (`utils/handle-host.ts`); an operator may also have filled `hosts` (`server/src/sites/rules.ts`). At 0.7 it is `hosts[0]`, so the boot step of issue 4 pins the 0.6 effective host there, once: `H` is `FEDIVERSE_HANDLE_HOST`, else the host of `URL`. With an empty list it fills `[H, host of FRONTEND_URL]`; with a filled list it moves `H` to the front, adding it if absent. If another site holds `H` the boot stops with a message that names the variable (or `URL`). The host of `FRONTEND_URL` is added last when missing, or logged when another site holds it. The old handle's WebFinger keeps answering because the package finds the site by the host of the `acct:` resource and `H` is in its `hosts`; a site that never set the variable also gets the CMS host in its attribution list (a visible, harmless addition). **The step runs once:** it writes a marker, the plugin store key `plugin_fediverse` / `cut-over-0.7`, when it completes, and does nothing on a boot that finds it, so reordering `hosts` later in the Content Manager survives a boot with the variable still set (the boot only logs the warning). So no upgrade changes a handle.
8. **The frontend gates the whole fediverse on the default site's module** (`loadSiteCached(defaultLocale).site.modules.fediverse`, in its WebFinger route). Several sites in the frontend are a later record (ADR-0017, consequences), so no frontend issue is needed for the cut-over.

- **Version.** The package publishes as `0.7.0`, declaring core line `0.7` (standard, section 7). `micelio-cms` raises a MINOR, `0.7.0`, which #360 already ships with the site settings; issue 7 joins that release.
- **The boot migration.** A follower, a pending delivery and a stored key must survive. The package cannot ship a Knex migration (ADR-0017, amendment of 2026-10-23), so the backfills of issues 3 and 4 are name-based boot steps in the package's `bootstrap`: idempotent, self-contained and tested on a database that has followers, a queued message and a stored key. Strapi does not order plugins, so the package cannot assume the core's `bootstrap` ran first. On an upgraded database the default site already exists (the core has created it since 0.6), so the backfill in the package's `bootstrap` finds it and does nothing when no site exists yet; on a fresh instance the `siteCreated` hook with `isDefault: true` creates the key entry. Issue 3 tests a boot where the package's `bootstrap` runs before the core's.
- **The proof.** Issue 7 runs `npm run test:upgrade` from the last `0.6` image with followers seeded and compares the counts before and after, as #360 does.
- **Out of scope here:** the UID change of the content types (the cut-over epic), the package's code, and any change in `micelio` other than naming the issue that needs it (none does).
