# Testing

Moved from `CLAUDE.md` (#113); the text is unchanged.

**Testing** (`tests/`) boots a real Strapi instance per suite (`tests/strapi.ts`) against an isolated SQLite file per Jest worker (`.tmp/test-<worker>.db`; `DATABASE_FILENAME` must stay relative to the project root), not mocks — `setupStrapi()`/`cleanupStrapi()` in `beforeAll`/`afterAll` (`cleanupStrapi()` waits for the connection pool to go quiet before destroying it: a successful write leaves queued work, and destroying the pool under it is an unhandled `Error: aborted` that kills Jest before it prints a summary, which is what a test expecting a rejected write hits when the write succeeds). Suites are TypeScript under `strict`: Jest only transpiles them (`tests/helpers/esbuild-transformer.js`, which also converts the ESM-only packages listed in `jest.config.js`, such as `structured-field-values`, which the fediverse package loads), and `npm run typecheck` checks them through `tests/tsconfig.json`. Jest globals are imported from `@jest/globals`; response shapes live in `tests/helpers/api-types.ts`; inputs that are invalid on purpose carry `// @ts-expect-error` with the reason. Set env vars a suite needs in `beforeAll`, before `setupStrapi()`: imports are hoisted above top-level statements. The fediverse code and its suites live in the package (`bogd3v/micelio-plugin-fediverse`, `test/`); this repository keeps `tests/fediverse-package.test.ts` (the distribution boots with the package: the plugin listing, WebFinger, the actor, a delivery to a fake inbox, who sees the profile, the refused boots), `tests/fediverse-disabled.test.ts`, `tests/fediverse-header-migration.test.ts`, `tests/rate-limit-fediverse.test.ts` and `tests/response-fields-fediverse.test.ts`. They force `FEDIVERSE_ENABLED=true` before Strapi boots, since the package reads it when it loads, and wait for what a delivery leaves in a fake inbox with `waitUntil` (Fedify allows private addresses only when `NODE_ENV=test`). The package reads `FEDIVERSE_ACTOR_IDENTIFIER` when its module loads, so a test that boots without it calls `jest.resetModules()` first. `tests/jest.global-setup.js` compiles the sources into `dist/` once per run and every suite boots from that output: compiling in each suite made parallel workers overwrite each other's files. `npm test` runs the workers in parallel; `npm run test:handles` adds `--detectOpenHandles`, which forces a serial run, to find leaked handles. `npm test -- tests/<file>` and `npx jest tests/<file>` run one suite.

The exact keys of every response the frontend reads from the content API are in `src/constants/response-fields/`, rendered in `docs/security/response-fields.md` (ASVS V15.3.1). The `tests/response-fields-*.test.ts` suites seed one fully populated record per content type and fail when a response carries a key that is not listed there, or lacks a required one. After changing the constants, regenerate the document with `npm run docs:response-fields` (it runs `UPDATE_RESPONSE_FIELDS_DOC=1 npx jest tests/response-fields-docs.test.ts`); the docs test fails until you do. `tests/data-classification.test.ts` checks `src/constants/data-classification.ts` against the schemas Strapi loads and against `docs/security/data.md` (ASVS V14.2.4): every attribute of a classified type has a level, every Restricted one is private or token-only, and every Restricted or Personal one is named in the document. `tests/frontend-queries.test.ts` compares the frontend's populate constants, copied into `tests/helpers/frontend-queries.ts`, with a micelio checkout at `../micelio` and is skipped when there is none.

## Against PostgreSQL

Production runs PostgreSQL, and `tests/strapi.ts` runs the suites on it when `TEST_DATABASE_URL` is set (`postgres://user:pass@127.0.0.1:5432/postgres`; each Jest worker gets its own database, `strapi_test_<worker>`, dropped and recreated at start). Run the whole suite with `npm run test:postgres`: it is `jest --forceExit --runInBand`, serial.

Do not run it in parallel (`npm test` or `npx jest` with `TEST_DATABASE_URL`). Booting Strapi on an empty database creates every table and index in one transaction, and each holds a lock until the commit. PostgreSQL keeps all locks in one shared table of `max_locks_per_transaction * (max_connections + max_prepared_transactions)` slots (64 * 100 = 6400 by default). One boot peaks near 2900 of them, so with a dozen workers booting at once the table fills and the server answers `error: create table "public"."strapi_core_store_settings" (...) - out of shared memory`; whichever suites boot at that moment fail whole, which is why the failing suites differ from run to run and each passes alone (#336). A bigger `max_locks_per_transaction` would let more workers boot together but depends on the server, so the documented command is the serial one. A run of the whole suite took 465 s in #336 on a quiet machine (122 suites then; there are more now) and 2957 s on a loaded one.

## Upgrade check

`npm run test:upgrade` (`scripts/upgrade-check/`, #369) proves that an upgrade from a released image keeps the data. It needs Docker and Node, takes a few minutes (it builds the image of the working tree) and is not part of `npm run check`.

It starts PostgreSQL 18 and `UPGRADE_FROM_IMAGE` (default `ghcr.io/bogd3v/micelio-cms:0.6.0`) with `MICELIO_DEMO=true`, `FEDIVERSE_ENABLED=true` and `FEDIVERSE_ACTOR_IDENTIFIER=blog` (both images run with federation on), waits for `GET /_health` to answer `204` (polling, bounded by `CHECK_TIMEOUT_SECONDS`, default 300), fetches the actor once (the released image stores its key then), stops the CMS, seeds the fediverse rows below, counts, starts `UPGRADE_TO_IMAGE` (default: a `docker build` of the working tree) on the same database, waits again and counts again. It prints one table (name, before, after) and exits `1` when any count fell, or when the released image left no rows in `abouts`, `articles`, `authors`, `categories`, `pages` or `tags`, in the fediverse tables below or in the key and grants below (the seed did not run, so the comparison would prove nothing).

What it counts, with `psql` in the database container:

- Rows of every table the released image created in the database, found by listing the `public` schema before the upgrade, except Strapi's bookkeeping (`strapi_migrations`, `strapi_migrations_internal`, `strapi_database_schema`, `strapi_core_store_settings`) and the permission tables below. This covers content tables, `_lnk` and `_cmps` tables and component tables, and a content type the new code retires, which then drops to zero. The `collectionName` of the schemas of `src/api/*`, plus `categories` and `tags` of the core plugin (`@micelio/strapi-plugin-core`, which this tree does not declare), adds the tables the working tree declares and their link tables.
- `up_permissions` and `strapi_api_token_permissions`, one row per action prefix (the action without its last segment, e.g. `api::article.article`), `admin_permissions` per `subject`, and the permission-to-role and permission-to-token link tables (`up_permissions_role_lnk`, `admin_permissions_role_lnk`, `strapi_api_token_permissions_token_lnk`), so a permission that is unlinked from its role or token shows.
- One row (`core_store:<key>`, count 1) for each `strapi_core_store_settings` key that starts with `plugin_content_manager_configuration_content_types::`.

The fediverse part (`scripts/upgrade-check/fediverse.mjs`, #391) proves that the move of the plugin from local code to the package loses nothing. After the first image is healthy and stopped, the check seeds with SQL a follower, an interaction, a federated article, a message in Fedify's queue (`fedify_message_v2`, with a delay of a year so no worker sends it: Fedify refuses private addresses outside `NODE_ENV=test`, so a delivery to a fake inbox cannot run against the images) and the grants `plugin::fediverse.read` and `plugin::fediverse.manage` on the Editor role. It counts the rows of `fediverse_followers`, `fediverse_interactions`, `fediverse_federated_articles` and `fedify_message_v2` (they are in the tracked tables), the stored actor key (`core_store:plugin_fediverse_keyPairs`, 1 when the key exists, never its value) and the admin permissions of each action that starts with `plugin::fediverse.` (`admin_permissions_action:<action>`).

It also compares the single type `site-setting` (hidden since 0.7 and only read by the boot copy) with the default site of the core (`scripts/upgrade-check/site-copy.mjs`, #415). The released image has no theme pin and no fediverse profile, so the check gives the single type both with SQL while the CMS is stopped, then, after the upgrade, prints the name, `themeId`, `themeVersion`, `themeDigest` and fediverse `username` of both, per locale, and exits `1` when any differs or the site lacks the locale (`docs/architecture/site-settings.md`, "Where each setting lives after the copy").

A name missing on one side counts 0 there. Reading a drop: the last column says `DROP` for a count that fell. A deliberate cut-over (a content type retired or renamed) lists the names it removes with `--allow-drop <name>` (repeatable, `npm run test:upgrade -- --allow-drop <name>`); the output repeats them and marks them `allowed`. Anything else is a loss of data or of a permission: find the migration or the bootstrap step that removed it.

From `0.6.0` to `0.7.0` the single type `api::site-setting` is hidden (#417): Strapi removes the admin permissions it had, which are the two rows the check reports, so the run lists them: `npm run test:upgrade -- --allow-drop admin_permissions:api::site-setting.site-setting --allow-drop admin_permissions_role_lnk` (11 and 3 rows of the first, 269 and 261 of the second on the demo content; the `site_settings` rows themselves stay, and the default site carries their values). Without the two flags the run exits `1`.

The secrets are generated at run time by `scripts/demo-secrets.js` of the image under a volume and are never printed; the output carries no token, address or email, and a failed start does not dump the container logs (rerun with `CHECK_KEEP=1`, which keeps the stack and prints how to remove it, and read them with `docker logs`). Every container, volume and network of a run carries the label `org.micelio.upgrade-check=<run id>`, and the script removes exactly those, and the image it built, also when it fails or is interrupted: SIGINT and SIGTERM stop the commands in flight, then cleanup finds everything by the label (containers in any state, volumes, networks, images) and looks again until nothing appears, so it does not depend on what the script had recorded. Cleanup's `docker` commands run in their own process group, so the Ctrl-C of a terminal, which reaches the whole foreground group, cannot kill them; a listing or removal that still fails is retried, and the exit code is 128 plus the signal (130 for SIGINT, 143 for SIGTERM). `tests/upgrade-check.test.js` and `tests/upgrade-check-site-copy.test.js` test the counting and comparing; the Docker run itself is not in Jest.
