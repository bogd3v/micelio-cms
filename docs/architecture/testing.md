# Testing

Moved from `CLAUDE.md` (#113); the text is unchanged.

**Testing** (`tests/`) boots a real Strapi instance per suite (`tests/strapi.ts`) against an isolated SQLite file per Jest worker (`.tmp/test-<worker>.db`; `DATABASE_FILENAME` must stay relative to the project root), not mocks — `setupStrapi()`/`cleanupStrapi()` in `beforeAll`/`afterAll` (`cleanupStrapi()` waits for the connection pool to go quiet before destroying it: a successful write leaves queued work, and destroying the pool under it is an unhandled `Error: aborted` that kills Jest before it prints a summary, which is what a test expecting a rejected write hits when the write succeeds). Suites are TypeScript under `strict`: Jest only transpiles them (`tests/helpers/esbuild-transformer.js`, which also converts the ESM-only packages listed in `jest.config.js`, such as Fedify's `structured-field-values`), and `npm run typecheck` checks them through `tests/tsconfig.json`. Jest globals are imported from `@jest/globals`; response shapes live in `tests/helpers/api-types.ts`; inputs that are invalid on purpose carry `// @ts-expect-error` with the reason. Set env vars a suite needs in `beforeAll`, before `setupStrapi()`: imports are hoisted above top-level statements. Fediverse tests force `FEDIVERSE_ENABLED=true` before Strapi boots since env vars are read at plugin-registration time, and run against `tests/helpers/remote-actor.ts`, a fake remote server that serves a signed actor and records what the plugin delivers to its inbox (`allowPrivateAddress` is enabled only when `NODE_ENV=test`). `tests/jest.global-setup.js` compiles the sources into `dist/` once per run and every suite boots from that output: compiling in each suite made parallel workers overwrite each other's files. `npm test` runs the workers in parallel; `npm run test:handles` adds `--detectOpenHandles`, which forces a serial run, to find leaked handles. Run `npm run build:fediverse` first when using `npx jest` directly — the `pretest` hook, which builds the plugin bundle, only runs with `npm test`; `npm test -- tests/<file>` runs one suite with it.

The exact keys of every response the frontend reads from the content API are in `src/constants/response-fields/`, rendered in `docs/security/response-fields.md` (ASVS V15.3.1). The `tests/response-fields-*.test.ts` suites seed one fully populated record per content type and fail when a response carries a key that is not listed there, or lacks a required one. After changing the constants, regenerate the document with `npm run docs:response-fields` (it runs `UPDATE_RESPONSE_FIELDS_DOC=1 npx jest tests/response-fields-docs.test.ts`); the docs test fails until you do. `tests/data-classification.test.ts` checks `src/constants/data-classification.ts` against the schemas Strapi loads and against `docs/security/data.md` (ASVS V14.2.4): every attribute of a classified type has a level, every Restricted one is private or token-only, and every Restricted or Personal one is named in the document. `tests/frontend-queries.test.ts` compares the frontend's populate constants, copied into `tests/helpers/frontend-queries.ts`, with a micelio checkout at `../micelio` and is skipped when there is none.

## Upgrade check

`npm run test:upgrade` (`scripts/upgrade-check/`, #369) proves that an upgrade from a released image keeps the data. It needs Docker and Node, takes a few minutes (it builds the image of the working tree) and is not part of `npm run check`.

It starts PostgreSQL 18 and `UPGRADE_FROM_IMAGE` (default `ghcr.io/bogd3v/micelio-cms:0.5.0`) with `MICELIO_DEMO=true`, waits for `GET /_health` to answer `204` (polling, bounded by `CHECK_TIMEOUT_SECONDS`, default 300), counts, stops the CMS, starts `UPGRADE_TO_IMAGE` (default: a `docker build` of the working tree) on the same database, waits again and counts again. It prints one table (name, before, after) and exits `1` when any count fell, or when the released image left no rows in `abouts`, `articles`, `authors`, `categories`, `pages` or `tags` (the demo seed did not run, so the comparison would prove nothing).

What it counts, with `psql` in the database container:

- Rows of every table the released image created in the database, found by listing the `public` schema before the upgrade, except Strapi's bookkeeping (`strapi_migrations`, `strapi_migrations_internal`, `strapi_database_schema`, `strapi_core_store_settings`) and the permission tables below. This covers content tables, `_lnk` and `_cmps` tables and component tables, and a content type the new code retires, which then drops to zero. The `collectionName` of the schemas of `src/api/*`, plus `categories` and `tags` of the core plugin (`@micelio/strapi-plugin-core`, which this tree does not declare), adds the tables the working tree declares and their link tables.
- `up_permissions` and `strapi_api_token_permissions`, one row per action prefix (the action without its last segment, e.g. `api::article.article`), `admin_permissions` per `subject`, and the permission-to-role and permission-to-token link tables (`up_permissions_role_lnk`, `admin_permissions_role_lnk`, `strapi_api_token_permissions_token_lnk`), so a permission that is unlinked from its role or token shows.
- One row (`core_store:<key>`, count 1) for each `strapi_core_store_settings` key that starts with `plugin_content_manager_configuration_content_types::`.

A name missing on one side counts 0 there. Reading a drop: the last column says `DROP` for a count that fell. A deliberate cut-over (a content type retired or renamed) lists the names it removes with `--allow-drop <name>` (repeatable, `npm run test:upgrade -- --allow-drop <name>`); the output repeats them and marks them `allowed`. Anything else is a loss of data or of a permission: find the migration or the bootstrap step that removed it.

The secrets are generated at run time by `scripts/demo-secrets.js` of the image under a volume and are never printed; the output carries no token, address or email, and a failed start does not dump the container logs (rerun with `CHECK_KEEP=1`, which keeps the stack and prints how to remove it, and read them with `docker logs`). Every container, volume and network of a run carries the label `org.micelio.upgrade-check=<run id>`, and the script removes exactly those, and the image it built, also when it fails or is interrupted: SIGINT and SIGTERM stop the commands in flight, then cleanup finds everything by the label (containers in any state, volumes, networks, images) and looks again until nothing appears, so it does not depend on what the script had recorded. Cleanup's `docker` commands run in their own process group, so the Ctrl-C of a terminal, which reaches the whole foreground group, cannot kill them; a listing or removal that still fails is retried, and the exit code is 128 plus the signal (130 for SIGINT, 143 for SIGTERM). `tests/upgrade-check.test.js` tests the counting and comparing; the Docker run itself is not in Jest.
