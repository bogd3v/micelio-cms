# Authentication pathways and sessions

**Kind:** reference. Goal: know every way a credential is accepted, what it takes to get one, how long it lives and how it ends. It covers the requirements V6.1.2, V6.1.3, V6.3.3, V6.3.4, V7.1.1, V7.1.2, V7.3.1 and V7.4.5 of [`asvs.md`](asvs.md). Reader accounts are described in [`../ACCOUNTS.md`](../ACCOUNTS.md), API tokens in [`../API_TOKENS.md`](../API_TOKENS.md) and the limiter in [`../RATE_LIMITING.md`](../RATE_LIMITING.md); this page does not repeat them, it puts their controls side by side.

Facts were read in this repository (`main`, the commit of the pull request that adds this page) and in the packages it installs: `@strapi/core`, `@strapi/admin` and `@strapi/plugin-users-permissions` 5.56.0. A value that comes from a Strapi default and not from `config/` is marked as such. A change of Strapi version re-checks the numbers.

## Pathways

There are two kinds of person (a **reader**, who has an account on the site, and an **admin**, who edits the CMS) and two kinds of machine credential (content-API tokens and admin tokens). Every route that accepts a credential is in this table.

### Reader email confirmation

The confirmation token has no expiry in the plugin (`controllers/auth.js:605-634` looks it up and clears it, with no time check). It stays valid until it is used or until a new confirmation is sent, which replaces it (`services/user.js:179-181`). It is the one reader token without a lifetime. The link confirms only the address it was sent to. Confirmation runs on a `GET`, which [`asvs.md`](asvs.md) records as V3.5.3, tracked in #178.

## Passwords

### Readers

- **Minimum length:** 8 characters, counted as code points, on sign-up, reset and change. `validationRules.validatePassword` in `config/plugins.ts:87-90` runs `createPasswordValidator` (`src/utils/password-rules.ts`), which the plugin calls from `controllers/validation/auth.js:19-48` (`@strapi/plugin-users-permissions` 5.56.0). Tested in `tests/password-rules.test.ts` and `tests/accounts.test.ts` (V6.2.1). Accounts an administrator creates or edits in the content manager skip these checks: that route validates the password with `min(1)` only (`controllers/content-manager-user.js:76`, `:129`; `controllers/validation/user.js:27` create, `:35` update). See the accepted risks.
- **Maximum length:** 72 bytes of UTF-8, enforced on sign-up, reset and change, not on sign-in. bcrypt uses only the first 72 bytes of the input, so input after the 72nd byte is ignored: a stored password of exactly 72 bytes accepts any longer string that starts with it. V6.2.8 is an accepted risk (below). V6.2.9, which asks for 64 characters, holds for ASCII; 64 multi-byte characters can pass 72 bytes, and stays open in #177.
- **Composition:** none. Known as V6.2.5 in [`asvs.md`](asvs.md).
- **Storage:** bcrypt through `bcryptjs` 2.4.3 (`services/user.js:161-162`).
- **Common passwords:** a password is refused when, folded to lower case and NFKC, it is one of the 3000 most common (`src/constants/common-passwords.ts`, from SecLists; the 498 of 8 or more characters, because shorter ones fail the minimum) (V6.2.4).
- **Breached passwords:** a password is refused when it is among 45,986 more passwords of 8 or more characters taken from the 100,000 most used in breaches (`src/constants/breached-passwords.ts`, NCSC list in SecLists) (V6.2.12). The check is local: no password or hash leaves the server (see [`outbound.md`](outbound.md)). It covers the most frequent breached passwords, not every breach; a service such as Have I Been Pwned would cover more, at the cost of a call to a third party for every password set.

### Admins

- At least 8 characters, at most 72 bytes, with a lowercase letter, an uppercase letter and a digit. These rules come from `@strapi/admin` and cannot be changed from this repository.
- No common-password, context-word or breached-password check: the admin validators have no hook (see the accepted risk below).

### Context-specific words (V6.1.2)

**Reader passwords** may not contain `micelio` or `strapi`, nor any word of `PASSWORD_BANNED_WORDS` (comma separated, 4 or more characters each; a word with spaces is also banned without them, for example the site and organisation names), compared in lower case and NFKC (`src/constants/password.ts`, `src/utils/password-rules.ts`). The message says the password has a word tied to the site, never which one. **Admin passwords** are not checked. The check is enforced at password set (V6.2.11).

### Multi-factor authentication (V6.3.3)

**Accepted risk.** Neither readers nor admins have a second factor. The installed `@strapi/admin` 5.56.0 has no two-factor code in its server or its panel (a search for TOTP, MFA and two-factor finds only marketing images on the Settings pages). The compensating controls are:

- sign-in is limited per client and per login identifier or admin email, across all clients, so one account cannot be guessed from many addresses (`auth-identifier`, `admin-identifier`; [`../RATE_LIMITING.md`](../RATE_LIMITING.md#per-account-limits));
- admin passwords must have 8 or more characters with three character classes;
- no default account exists: the first administrator is created by the operator (V6.3.2);
- admin sessions expire by idle time and by absolute time (see [admin sessions](#admin-sessions));
- the operator can block a reader or deactivate an admin at once.

Adding a second factor means a new feature, not a setting. It needs an ADR before code.

### Why the pathways are listed here

There is no other place where the pathways and their controls appear together. Each row above names the code that enforces the control. When a route is added or its limit changes, this table changes in the same pull request ([`asvs.md`](asvs.md), "Keeping it true").

## Sessions

### Reader sessions

- **Form:** a JWT signed with `JWT_SECRET`, algorithm HS256 only, payload `{ id, iat, exp }`. There is no `aud` and no token-type claim (`services/jwt.js:55-56`, `:80-91`), so the separation from admin tokens rests on the two secrets being different. The admin panel signs with `ADMIN_JWT_SECRET`, and boot refuses a missing or placeholder value in production (`src/utils/secrets.ts:43`).
- **Absolute lifetime:** 7 days from issue (`config/plugins.ts:86`). This is the value of `exp`, not a renewal.
- **Inactivity timeout:** none. Using the JWT does not extend it, and no refresh exists in this configuration (`controllers/auth.js:284` answers 404 in the default mode), so a reader signs in again after seven days whatever they did. This deviation is accepted; see [accepted risks](#accepted-risks).
- **Concurrent sessions:** unlimited. Every sign-in issues a JWT and the earlier ones stay valid until their `exp`, so one account can hold any number of sessions on any number of devices.
- **Revocation on a password change:** a reset or a change stamps `passwordChangedAt`, and `jwt.verify` refuses any JWT whose `iat` is earlier than that second (`src/extensions/users-permissions/reset-security.ts:48-52`, `:69-92`). The JWT returned by the change itself is in the same second and stays valid.
- **Per-session logout:** not available. `POST /api/auth/logout` and the session list and revoke routes answer 404 unless `jwtManagement` is `refresh` (`controllers/auth.js:317-321`, `:353-357`, `:368-372`). The configuration does not set it. Logging out is a client action: the frontend drops its JWT.

### Admin sessions

Admin sessions are server-side records (`@strapi/core` 5.56.0 `services/session-manager.js`): each has a random session id of 16 bytes (`:175`), an access token that lives 30 minutes (`@strapi/admin` `server/src/bootstrap.js:142`, the Strapi default), and a refresh cookie, `httpOnly` and `SameSite=Lax` by default (`@strapi/admin` `shared/utils/session-auth.js:38-61`). The panel renews the access token from the cookie. `config/admin.ts` sets no session options, so the defaults below apply.

| Setting           | Login without "remember me"    | Login with "remember me"       | Where it comes from                                                                                                                                                                                         |
| ----------------- | ------------------------------ | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Access token      | 30 minutes                     | 30 minutes                     | `bootstrap.js:142`                                                                                                                                                                                          |
| Idle timeout      | 2 hours since the last renewal | 14 days since the last renewal | `session-auth.js:35` and `:37`; enforced at each renewal against the creation time of the presented token (`session-manager.js:465-473`)                                                                    |
| Absolute lifetime | 30 days                        | 30 days                        | `bootstrap.js:143` and `:145`: the fallback is the `expiresIn` of the token options, `30d` (`services/token.js:11-13`). The 1-day constant in `session-auth.js:36` is not used by the default configuration |

- **Concurrent sessions:** allowed. A login does not end the user's other sessions (`controllers/authentication.js:67-72`).
- **Sessions that end with an event:** a reset ends all of the user's sessions (`controllers/authentication.js:198`); a password change in the profile ends all of them (`controllers/authenticated-user.js:51-53`); a logout ends all of the user's sessions when the request names no device, and only that device when it does (`controllers/authentication.js:256-280`).
- **Inactive or deleted admins:** an access token is refused at each request when the admin is inactive (`strategies/admin.js:55`) or its session is no longer active (`strategies/admin.js:42-45`). Deleting an admin ends its sessions (`services/user.js:369-371`, `:408-410`).

### Ending sessions as an administrator (V7.4.5)

What an admin can end, and how:

| Scope     | Readers                                                                                                                                                                                                                                                                                                                                                                         | Other admins                                                                                                                                                                                                          | The admin's own sessions                                                                                                                                  |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One user  | Set `blocked` on the user in the admin panel (Content Manager, Users & Permissions). The next request with any JWT of that user is refused (`@strapi/plugin-users-permissions` 5.56.0 `strategies/users-permissions.js:54-58`), and the user cannot sign in (`controllers/auth.js:176-178`). Deleting the user also refuses every JWT (`strategies/users-permissions.js:39-45`) | Deactivate (`isActive` off) or delete the admin. Both refuse the access token at once (`strategies/admin.js:55`); deletion also invalidates the refresh sessions (`services/user.js:369-371`)                         | The admin panel lists them and ends any one, or all but the current one (`controllers/authenticated-session.js:12-58`, routes in `routes/users.js:17-19`) |
| All users | Rotate `JWT_SECRET` and restart. Every reader JWT stops verifying (`services/jwt.js:85-91`). Every reader must sign in again, and no admin session is affected                                                                                                                                                                                                                  | Rotate `ADMIN_JWT_SECRET` and restart. Refresh and access tokens are signed with that secret (`@strapi/core` `services/session-manager.js:196`, `:234`, `:390`), so every admin session ends. Not exercised in a test | Logout without a device ends all of them                                                                                                                  |

The reader column is what the operator relies on; it is documented in [`../ACCOUNTS.md`](../ACCOUNTS.md#ending-a-readers-sessions) as well. There is no control to end one reader session and keep the others.

### Content-API and admin tokens

Tokens are not sessions. Their lifetime is chosen when the token is created, from unlimited, 7, 30 or 90 days (`@strapi/admin` `services/constants.js:20-25`, `services/api-token.js:580-588`). The content-API strategy and the admin token strategy both check it on every request (`strategies/content-api-token.js:37`, `strategies/admin-token.js`). Revoking a token is deleting it in the admin panel. The strategies look the token up on each request, so the next request is refused.

## Accepted risks

Each risk names what it is, why it is accepted and what limits it. Accepting a risk does not close the requirement's issue; it records the decision.

| Requirement                             | Risk                                                                                                                                       | Reason                                                                                                                                   | Compensating controls                                                                                                                                                                                                                           |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V6.2.1, V6.2.4, V6.2.11 content manager | A reader account created or edited by an administrator in the content manager is not checked against the reader password rules             | The route belongs to the plugin's admin controller and has its own validator; the rules are not configurable there                       | Only administrators reach it, and a reader whose password an administrator set can change it with `change-password` (which is checked)                                                                                                          |
| V6.2.8 password truncation              | bcrypt compares only the first 72 bytes at sign-in, so a stored password of exactly 72 bytes accepts any longer string that starts with it | The 72 bytes are a limit of bcrypt. Refusing longer input at sign-in would lock out an account that signed in this way and force a reset | New passwords over 72 bytes are refused at set time, so the case needs a password of more than 72 bytes, which only exists if an administrator set it in the content manager, and still the whole first 72 bytes to guess; sign-in limits apply |
| V6.2.4, V6.2.11, V6.2.12 admins         | Admin passwords skip the common-password, context-word and breached-password checks                                                        | `@strapi/admin` 5.56.0 has no hook for them; intercepting its routes here would duplicate its validators                                 | Few accounts, set by the operator; 8 characters with three character classes; sign-in limits per client and per admin email                                                                                                                     |
| V6.3.3 multi-factor                     | Single factor for readers and admins                                                                                                       | No second factor in Strapi Community 5.56.0; adding one is a feature with its own design                                                 | Per-client and per-identifier sign-in limits, admin password rules, no default account, idle and absolute admin expiry, block and deactivate                                                                                                    |
| V7.3.1 inactivity                       | Reader JWTs have no inactivity timeout, only a 7-day absolute lifetime                                                                     | Short access tokens need `jwtManagement: 'refresh'`, a change the frontend must follow (see [`../ACCOUNTS.md`](../ACCOUNTS.md))          | 7-day `exp`, revocation by block, `JWT_SECRET` rotation, revocation on password change. Admins have idle timeouts (2 hours or 14 days)                                                                                                          |
| V7.1.2 concurrent sessions              | Unlimited reader sessions per account                                                                                                      | Readers use several devices. Known gaps that are **not** accepted and stay open in [`asvs.md`](asvs.md) (issue #177): V6.2.5, V6.2.9, V7.2.4 (a new sign-in does not end older reader JWTs), V7.4.1 (logout is not available), V7.5.1 (an admin can change their email without the password) and V7.5.2 (readers cannot list their sessions), V9.2.2 and V9.2.3 (no token-type or audience claim).

## Keeping it true

- A new pathway, a new limit or a new lifetime changes the table above in the same pull request.
- A change of Strapi version re-reads the numbers marked as defaults (`bootstrap.js`, `session-auth.js`, `services/token.js`, `services/constants.js`), since the code that sets them is in `node_modules`.
- The reader numbers are in `config/plugins.ts` and `config/rate-limit.ts`, the admin numbers in `config/admin.ts`. A value set there overrides the defaults above.
