# Data classification and protection

**Kind:** reference. The data the CMS holds, the three protection levels it sorts them into, and what each level requires. Answers ASVS 5.0.0 V14.1.1 and V14.1.2 ([mapping](asvs.md)). The levels and their names match the frontend's [data.md](https://github.com/bogd3v/micelio/blob/main/docs/security/data.md) (micelio); the keys are in [keys.md](keys.md), the outbound destinations in [outbound.md](outbound.md) and the logs in [logging.md](logging.md).

## Levels

| Level          | What it is                                                               | Requirements                                                                                                                                                                                                                                                                                                   |
| -------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Restricted** | A credential or a single-use secret: whoever holds it can act as someone | Never returned by an API (Strapi's `private` attributes), never logged, never in a response to another person. At rest only as a hash or an encrypted value, where the table below says so. Single use or time limited where the code can enforce it.                                                          |
| **Personal**   | Data about an identifiable person                                        | Collected because a feature needs it. Returned only to the person it describes, or to moderators and editors in the admin panel. Not logged, except numeric ids and keyed hashes. Leaves the CMS only to a provider the operator configured (see [outbound.md](outbound.md)). Kept while its feature needs it. |
| **Public**     | Published content and aggregated counts                                  | Served by the content API as published. Drafts are not public: only editors read them ([drafts.md](../architecture/drafts.md)).                                                                                                                                                                                |

## How it is checked

`src/constants/data-classification.ts` gives every attribute of the types above a level, and `tests/data-classification.test.ts` boots a real Strapi and fails when:

- an attribute of a classified type has no level (a new attribute must be classified in the pull request that adds it), or a level names an attribute that no longer exists;
- a Restricted attribute is neither `private` nor on a type that no role may read, or a response of `src/constants/response-fields/` lists it where a token holder does not read it;
- a Restricted or Personal attribute is not named in the "Where" cell of a row of "What is held" under its own content type.

The third check reads the table. In a "Where" cell, a content type is written as its UID in a code span (`plugin::comments.comment`), and the attributes that follow it, in code spans, up to the next UID, belong to it. A name under another type, or in prose or another column, does not count. This is the convention to keep when adding a row.

It is a floor, not a review. It does not check that a row's level or protection text is right, and it does not read attributes written outside a code span. Whether the stated protection holds is for [asvs.md](asvs.md) V14.2.4 to track.

## Gaps

This requirement of the levels is not met yet. It is why V14.2.4 stays open ([mapping](asvs.md)); it is tracked in #181.

- Blocked unconfirmed accounts are kept without a time limit, on purpose: deleting one would free its address and let it register again, escaping the block. The purge also does nothing for accounts when `email_confirmation` is off, because unconfirmed users can then sign in. An operator who wants them gone deletes them in the admin panel.
