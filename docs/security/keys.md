# Keys, secrets and algorithms

**Kind:** reference. What the CMS holds as a secret, who may hold it, what each one signs or encrypts, what a rotation breaks and which algorithms the CMS uses. Answers ASVS 5.0.0 V11.1.1 and V11.1.2 ([mapping](asvs.md)). The frontend's side is `docs/security/keys.md` in micelio; its names (`NUXT_STRAPI_API_TOKEN`, `NUXT_STRAPI_FORWARDER_SECRET`) are the frontend's copies of the CMS variables listed here.

## Policy

- **Owner.** The site operator owns every secret. The repository, the image and `.env.example` hold names and no values. `npm run generate:keys` prints fresh values to standard output; it writes nothing.
- **Where a secret lives.** In the environment of the container, or in the hosting platform's secret store. Never in the repository, a fixture, a log, an image layer, a build argument or an issue (standard, section 5). The demo's values go to the `demo-secrets` volume (`scripts/demo-secrets.js`, [install.md](../operate/install.md)).
- **Strength.** Random values from a CSPRNG of at least 32 characters. The production boot refuses a missing, placeholder or shorter Strapi secret (`src/utils/secrets.ts:11-12`, `:43-60`, called from `src/index.ts:51`); the forwarder secret refuses boot below 32 characters (`src/constants/rate-limit.ts:9`, `src/utils/rate-limit/runtime.ts:37-38`); the two API token keys are refused below 32 characters (`src/migrations/api-tokens.ts:73`, `:108-110`). Nothing is derived from a password.
- **Lifetime.** Nothing expires on its own. The recommended rotation is at least every 90 days, at once after an exposure, and when someone who held a value leaves. The project does not enforce the interval.
- **Lifecycle.** Generate, set the new value, restart (CMS first, then the frontend), and remove the old value from the environment and the secret store. A value that was printed, pasted or committed is treated as exposed.
- **Review.** This inventory is reviewed in the pull request that adds, removes or changes a secret, an algorithm or a key's use.

## Rotating `ENCRYPTION_KEY`

With `FEDIVERSE_ENABLED=true` the actor's private key is encrypted with `ENCRYPTION_KEY`, so this value now also holds the blog's fediverse identity. After a change the stored key no longer decrypts and federation fails closed: the actor document and WebFinger answer `500`, an inbox delivery that needs a signed answer (the `Accept` of a `Follow`) answers `500` without sending it, and no outgoing activity is signed. Those answers carry only the generic body `Internal Server Error`, so a visitor cannot tell that the key is the problem. The cause, naming `ENCRYPTION_KEY`, is logged at `error` level at most once a minute, so crawlers that keep fetching the actor do not fill the log; the line never contains key material or a stack. The CMS never replaces the stored key on its own, so putting the old value back restores federation as it was. Tests: `tests/fediverse-actor-key-encryption.test.ts` (actor, WebFinger and inbox answers, the `Accept` of a `Follow`, one log line per minute).

There is no re-encryption command yet. Until there is one, choose:

- **Keep the identity.** Do not rotate `ENCRYPTION_KEY` on an instance that federates unless it was exposed. After an exposure treat the actor key as exposed too, because whoever holds the database and the old value can sign as the blog.
- **Accept a new identity.** Change the value, then delete the core store row `plugin_fediverse_keyPairs`; the next request generates a new pair (see the cost below).

**Strength.** The AES key is the SHA-256 of `ENCRYPTION_KEY`, with no key-derivation function, as in Strapi's own encryption service. That is adequate only because the value is a random secret of high entropy: use the 32 random bytes (256 bits) that `npm run generate:keys` prints, never a password or a phrase, which a stolen database would let anyone guess offline. The boot checks length only (`src/utils/secrets.ts`), not randomness. The IV is 16 random bytes, not GCM's usual 12: GCM accepts any IV length (it hashes a length other than 12 into the counter block), and with random IVs the collision bound stays far beyond the handful of encryptions a key pair ever gets.

## The actor key written before encryption

Encryption at rest protects what is written from the upgrade on. Everything written before it still holds the private JWK in plain text:

- database backups and dumps taken before the upgrade;
- free space in the database files: PostgreSQL keeps the old row version as a dead tuple until `VACUUM` reuses the space, and in its write-ahead log and any WAL archive; SQLite keeps the old page in the file's free pages until `VACUUM`.

So either destroy those copies (old backups, WAL archives, and a `VACUUM FULL` of `strapi_core_store_settings` in PostgreSQL or a `VACUUM` in SQLite), or treat the actor key as exposed.

Rotating the actor key is the only way to make an exposed one worthless, and it means a new federated identity: the actor id stays, but remote servers verify the blog's signatures with the copy of the old public key they cached until they fetch the actor again, so deliveries can be refused meanwhile and some servers may need followers to follow again. How each server reacts was not verified. The CMS does not rotate the key on upgrade; the operator decides, weighing who could have read the old copies against the cost to followers. To rotate, delete the core store row `plugin_fediverse_keyPairs`; the next request generates and encrypts a new pair.
